# 체크리스트 ↔ web-runner 연결 전략

SharePoint 의 `GME QA Checklist V2.1.xlsx` 를 web-runner 에 붙이는 계획이다.
매핑 작업이 끝나면 이 문서의 "계약" 절에 맞춰 붙인다.

작성 2026-09-30. 실측 기준: `Checklist(Basshu)` 시트 / `run_suite.ps1` 41항목 / 앱 7.21.0-stag.

---

## 0. 지금 있는 것 (실측)

**체크리스트(정본, SharePoint)**
- 시트 `Checklist(Basshu)` — 헤더 8~9행, 데이터 **11~423행(413행)**
- 열: `B` Priority / `C·D·E` 1~3Depth / `F` Checklist(확인 문구) / `J` Comment
- 릴리스 결과 묶음: `H8` = `2026.09.23 GME App 7.21.0 (NewApp)`,
  그 아래 `H9` = iOS Result, `I9` = **Android Result**
- ⚠️ **ID 열이 없고 `자동화결과` 시트도 없다.** 아직 재구성 전이다.

**도구**
| 파일 | 하는 일 | 한계 |
|---|---|---|
| `gme_excel.py` | Graph `range()` PATCH 로 셀 단위 읽기·쓰기 | 개인 OAuth (아래 §5) |
| `Checklist/build_checklist_structure.py` | `REG-001` 식 ID 부여 + yaml 매핑 제안본 생성 | 제안본을 만들 뿐, 정본에 반영은 별도 |
| `Checklist/write_result.py` | ID 로 행, 머리글 문구로 열을 찾아 결과 기입 | **로컬 xlsx 전용** (아래 §4) |

**자동화 결과**
- `run_suite.ps1` → `suite_logs\<시각>\SUMMARY.md`
- 항목(=플로우) 단위 `PASS/FAIL/SKIP` + 스텝수·소요·사유
- 케이스 단위는 **합계만** 나온다: `케이스 단위 제외: BLOCKED n / N/A n`
- web-runner 는 이 SUMMARY.md 를 파싱해 이력을 그린다 (`runner.read_history`)

---

## 1. 핵심 문제 — 단위가 다르다

```
run_suite   41 항목(플로우)  →  PASS / FAIL / SKIP
체크리스트  413 행(확인 항목) →  Pass / Fail / N-A
```

**플로우 하나가 체크리스트 여러 행을 덮는다.** 그래서 두 가지가 곧바로 성립하지 않는다.

- 플로우가 FAIL 이라고 그 안 케이스가 전부 Fail 은 아니다 (앞부분은 통과했을 수 있다)
- 플로우가 PASS 라고 그 안 케이스가 전부 Pass 도 아니다 (BLOCKED·SKIP 이 섞인다)

→ **결과를 케이스 단위로 쪼개는 것은 별도 작업이다(§3 4단계).**
그 전까지는 **플로우 단위로만** 다루고, 그 사실을 화면과 기입값에 드러낸다.

---

## 2. 계약을 먼저 고정한다

매핑 파일이 오기 전에 정할 수 있고, 오면 **어댑터 한 겹**만 쓰면 된다.
web-runner 내부는 아래 세 가지 모양만 안다.

**① 체크리스트 행**
```json
{ "id": "TEL-001", "area": "Telecom", "depth": ["Telecom", "GME Mobile", ""],
  "priority": "High", "text": "홈화면 이동 확인", "row": 142 }
```
`row` 는 **표시·디버깅용일 뿐 키가 아니다.** 키는 항상 `id` 다.

**② 매핑**
```json
{ "id": "TEL-001", "flow": "18_Telecom", "case": "01" }
```
`case` 는 선택이다. 없으면 플로우 단위로만 다룬다.

**③ 결과**
```json
{ "id": "TEL-001", "result": "Pass", "source": "auto",
  "stamp": "2026-09-29_164807", "flow": "18_Telecom", "note": "" }
```
`source` 는 반드시 남긴다 — 사람이 넣은 값과 자동이 넣은 값을 구분하지 못하면
나중에 되돌릴 수가 없다.

## 3. 단계

### 1단계 — 읽기만. 커버리지 화면

web-runner 에 `/api/checklist` 를 추가한다. **쓰기 없음 → 정본이 망가질 일이 없다.**

- 테스트 목록 옆에 "체크리스트 N행" 배지
- 커버리지 탭: 영역별 덮힘/안 덮힘
- **안 덮힌 행 목록** ← 이게 이 단계의 진짜 산출물이다. 다음에 뭘 자동화할지가 여기서 나온다

**읽기는 캐시로 한다.** Graph 를 매 요청마다 부르지 않는다.

```
gme_excel.py get  →  web-runner/checklist_cache.json  →  /api/checklist
```

이유 셋:
- SharePoint 가 느리거나 인증이 끊겨도 **화면이 멈추지 않는다**
- 서버가 토큰을 상시 쥐지 않아도 된다 (쓰기 때만 필요)
- 매핑이 바뀐 시점이 파일 하나로 남아 "언제 기준 커버리지인지"가 분명해진다

캐시에 `fetched_at` 을 박고 화면에 표시한다. 오래됐으면 경고를 띄운다.

### 2단계 — 미리보기

실행이 끝나면 **"이번 실행이 체크리스트 어디를 어떻게 채울지"** 를 보여준다. 기입은 아직 안 한다.

이 단계가 따로 있는 이유: 매핑이 틀렸을 때 **정본을 건드리기 전에** 드러난다.
1단계의 커버리지 숫자는 매핑이 틀려도 그럴듯해 보이지만, 여기서는 행 문구와 실행 결과가
나란히 보여서 어긋남이 눈에 띈다.

### 3단계 — 기입

- 경로는 **`gme_excel.py`(Graph range PATCH)** 뿐이다 (§4)
- **PASS 일 때만 쓴다.** FAIL 은 칸을 채우지 않고 로그 링크만 남긴다 —
  실패는 사람이 봐야 하는 신호지 칸을 채울 정보가 아니다
- 미리보기 → 사람이 버튼 → 기입. 자동 기입 금지
- 기입과 **동시에** `자동화결과` 시트에 이력을 한 줄 덧붙인다
  (실행일시·릴리스·환경·플랫폼·빌드·기기·ID·결과·yaml·비고)
  → 결과 칸만 보면 출처를 알 수 없다. 이력이 있어야 되돌릴 수 있다

### 4단계 (선택) — 케이스 단위

Maestro `label:` 로 케이스 경계를 로그에 찍고 파서가 구간을 나눈다.

```yaml
- evalScript:
    script: ${true}
    label: "CASE-END TEL-001"
```

- ✅ **문법 확인됨**(2026-09-30, maestro 2.10.0 jar 실측):
  `YamlEvalScript` 필드 = `script` / `label` / `optional`,
  `EvalScriptCommand` 에 `label`·`getLabel` 존재 → 로그에 라벨이 대신 찍힌다.
  추측이 아니라 확인한 값이니 다시 따져볼 필요 없다.
- 저장소에 `label:` 사용이 **0건**이라 새 규약이다
- 41개 파일을 손대는 일이므로 **맨 마지막**에 한다
- 파일 단위로 점진 도입이 된다 — 마커가 없는 플로우는 그냥 "플로우 단위"로 남는다

## 4. ⛔ 하지 말 것

**행 번호로 묶지 말 것.** 행 하나 삽입에 전부 어긋난다.
`_bb_mapping.json` 의 "행 +1" 보정에서 이미 한 번 데였다. 키는 `id` 다.

**열 문자를 박지 말 것.** 릴리스가 추가될 때마다 결과 열이 밀린다.
현재 Android 결과가 `I` 인 것은 이번 릴리스 기준일 뿐이다.
`write_result.py` 처럼 **머리글 문구로 찾는다.**

**`write_result.py` 로 SharePoint 정본에 쓰려 하지 말 것.**
xlsx 를 zip 으로 열어 시트 XML 을 갈아끼우는 방식이라 **로컬 파일 전제**다.
OneDrive 동기화 업로드는 `UPLOAD FAILED` 로 막힌 기록이 있다.
→ 정본 쓰기는 `gme_excel.py` 경로. 동시편집 안전성도 거기서 나온다.
(단, `write_result.py` 의 **ID·머리글로 찾는 방식과 `--dry-run`** 은 그대로 가져올 값어치가 있다)

**FAIL 을 기입하지 말 것.** §3 3단계.

**`run_suite.ps1` 의 `$Suite` 표를 정본으로 믿지 말 것.**
`blocked`/`na`/`note` 는 **손으로 적는 메타데이터**라 낡는다.
2026-09-30 에 `18_Telecom` 이 그랬다 — 2026-09-03 변경과 2026-09-29 변경이 **둘 다** 빠진 채
`blocked=@("05","06","07")` 로 남아 있었다. 커버리지 집계에 그대로 흘러든다.
→ 이 표에서 값을 가져올 거면 **어긋남을 검사하는 장치**가 같이 있어야 한다
(예: yaml 의 케이스 마커 개수와 표의 케이스 번호가 맞는지).

## 5. 두 가지 위험

### 거짓 통과가 그대로 전파된다

체크리스트에 Pass 를 찍는다는 건 **"사람이 안 봐도 된다"**는 뜻이다.
그런데 이 저장소에는 거짓 통과 이력이 여럿 있다.

- `21_Card [13]~[19]` — EXIT=0 인데 토글이 하나도 안 움직였다
- `21_Card [21]` — `tapOn "카드 취소"` 뒤 `assertVisible "카드 취소"` 라 행 라벨이 남아 항상 통과
- `04_Menu_History` 인바운드 구간 — 실검증 없이 통과하고 있었다

자동 기입은 이런 것을 **릴리스 판단 근거로 승격시킨다.** 대책:

- `source: "auto"` 와 `자동화결과` 이력을 반드시 남긴다 (§2 ③, §3 3단계)
- 결과 칸에 실행 stamp 를 함께 남겨 **로그로 되짚을 수 있게** 한다
- 자동 Pass 가 처음 붙는 영역은 **한 번은 사람이 표본 확인**하고 넘어간다

### 인증이 개인 OAuth 다

토큰은 `~/.gme_excel_token.json` 이고 **본인 권한**으로 동작한다.
refresh 가 만료되면 `login` 이 브라우저를 띄워야 하는데 **서버는 그걸 못 한다.**

- web-runner 에 "SharePoint 연결됨/끊김" 상태와 재로그인 안내를 둔다
- 끊겨도 **1단계 화면은 캐시로 계속 동작해야 한다**
- 서버가 개인 토큰을 쥐게 되므로 **`127.0.0.1` 바인딩을 절대 풀지 말 것**
  (`server.py` 현재 그렇게 돼 있다 — 유지)
