## 2. 방향 — web-runner 가 엑셀의 "프론트엔드"가 된다

정본을 옮기는 것과 **엑셀을 안 보게 되는 것**은 다른 일이다. 후자만 먼저 한다.

- 매핑·편집·결과 확인을 전부 web-runner 화면에서 한다
- 고친 값은 **그 셀만** 엑셀에 PATCH 한다 (동시편집·서식·댓글 안전)
- 매핑은 엑셀이 아니라 **저장소**에 둔다 → 엑셀을 나중에 놓아도 남는다

이러면 "엑셀을 안 본다"가 달성되면서, 정본 이동에 딸려오는 부채(백업·이력·동시편집·접근성)를
지금 지지 않는다. 6개월 뒤 아무도 엑셀을 안 열게 되면 **그때가 옮기기 가장 싼 순간**이다.

### 양쪽 문을 열어두는 원칙 셋
1. **저장 형식을 엑셀에 묶지 않는다.** 중립 JSON + 엑셀 어댑터 한 겹. 떼면 그만이다.
2. **엑셀 고유 기능에 의미를 싣지 않는다.** 조건부 서식 색이나 셀 댓글에 판단을 담으면
   나중에 **옮길 수 없는 정보**가 된다. 판단은 값으로, 전용 필드에.
3. **읽기는 캐시로.** 엑셀이 느리거나 인증이 끊겨도 화면이 돌아야,
   "없어도 되네"가 실제로 체감되고 그게 판단 근거가 된다.

### "엑셀이 필요 없는 상태"의 조건
- [ ] 413행을 web-runner 에서 읽고 고칠 수 있다
- [ ] 릴리스가 여러 개 쌓인다 (엑셀은 열을 옆으로 늘려 이력을 남긴다)
- [ ] Priority · Depth · Comment 가 다 들어간다
- [ ] **iOS 결과를 기록할 자리가 있다** — iOS 도 추후 web-runner 로 실행한다
- [ ] 백업·되돌리기가 된다 (JSON 을 git 에 두면 대부분 공짜)
- [ ] 남에게 보여줄 방법이 있다 ← localhost 라서 이게 제일 오래 남는다

## 3. ID — 위치로 만들면 안 된다

`build_checklist_structure.py` 는 ID 를 위에서부터 센다.
```python
seq[code] += 1
d["id"] = "%s-%03d" % (code, seq[code])   # REG-001, REG-002 ...
```
**Registration 중간에 한 행이 삽입되면 그 아래 `REG-*` 가 전부 밀린다.**
`_bb_mapping.json` 의 "행 +1" 사고와 같은 문제가 옷만 갈아입은 것이다.

→ **ID 는 한 번 부여해 시트에 써 넣고 고정한다. 절대 재생성하지 않는다.**
   새 행은 그 영역 최대 번호 +1. 이게 안 되면 이 문서의 나머지가 전부 성립하지 않는다.

## 4. 결과 값 네 가지

정본에 실제로 쓰이는 값만 쓴다. 셀렉트로 고정해 자유 입력을 막는다.

| 값 | 뜻 | 누가 넣나 |
|---|---|---|
| `Pass` | 확인했고 정상 | 자동 / 수동 |
| `Fail` | 확인했고 결함 | 수동 (**자동 Fail 은 확인 대기로 둔다** — §5) |
| `Not Test` | **자동화 불가** — 이번 실행으로 확인하지 못함 | 자동화 불가 행의 기본값 |
| `NA` | **해당 없음** — 확인할 화면·기능이 없음 | 자동 (`run_suite` 의 `na`) / 수동 |

⚠️ **`Not Test` 와 `NA` 를 섞으면 "남은 일"을 셀 수 없게 된다.**
`Not Test` = 못 했다(언젠가 해야 함) / `NA` = 할 것이 없다(영영 없음).

실제 예가 둘 다 있다:
- Telecom `[02]~[08]` = **`NA`** — 홈 그리드가 외부 웹으로 바뀌어 **확인할 화면이 없다**
- 생체인증 충전 = **`Not Test`** — **화면은 있는데 자동화가 못 닿는다**(사람이 하면 `Pass` 가 된다)

**화면에 보이는 글자가 곧 기입될 값이어야 한다.** `N-A` 로 보여주고 `NA` 를 쓰면
정본의 `pass`(소문자) 오염과 같은 부류의 사고가 난다.

## 5. 출처(provenance) — 값보다 중요하다

**모든 결과 칸은 셀렉트다. 자동으로 채워진 칸도 사람이 고칠 수 있다.**
외부 요인·셋팅 불량으로 Fail 이 났지만 사람이 보면 정상인 경우가 충분히 있다.

대신 **고치면 출처가 남는다.** 셀렉트만 두면 그 `Pass` 가 실행에서 나온 건지
사람이 고친 건지 나중에 알 수 없게 된다.

```
[ Pass  ▾ ]                    [ Pass  ▾ ]  ← 테두리 주황
자동 · 09-29 16:48              수동 덮음 · 자동은 Fail · 09-29 15:36
```

**자동 `Fail` 은 체크리스트에 바로 기입하지 않고 「확인 대기」로 둔다.**
외부 요인으로 난 Fail 이 릴리스 판단에 그대로 실려서도 안 되고,
조용히 묻혀서도 안 된다 → 사람이 최종값을 고르되 그 판단이 기록에 남는다.

**덮어쓸 때는 Comment 에 사유가 있어야 저장된다.**
3개월 뒤 같은 케이스가 또 Fail 날 때 "그때 왜 덮었더라"를 답할 수 있는 건 그 한 줄뿐이다.

Comment 규칙:
- 엑셀 `J` 열. **릴리스마다 열이 따로 없고 한 칸을 계속 쓴다** → 덮어쓰지 말고 **줄을 덧붙인다**
- 접두사는 기존 관례대로: `(aos)` / `- ios :` / `- aos/ios :`

## 6. 단위 불일치 — 41 vs 413

```
run_suite   41 항목(플로우)  →  PASS / FAIL / SKIP
체크리스트  413 행(확인 항목) →  Pass / Fail / Not Test / NA
```

플로우 하나가 여러 행을 덮는다. 그래서 둘 다 성립하지 않는다.
- 플로우 FAIL ≠ 그 안 케이스 전부 Fail (앞부분은 통과했을 수 있다)
- 플로우 PASS ≠ 그 안 케이스 전부 Pass (`Not Test`·`NA` 가 섞인다)

실패 지점 **이후** 케이스는 "확인함"이 아니라 **미확인**이다. Fail 로 싸잡으면 거짓 보고다.

→ **케이스 단위 분해는 별도 단계**(§10 4단계)다. 그 전까지는 플로우 단위로만 다루고
그 사실을 화면에 드러낸다.

## 7. 화면

### 결과 기준 (상단 셀렉트)
지금 보고 있는 결과가 **어느 실행의 것인지**를 정하는 단 하나의 셀렉트다.
```
결과 기준  [ 최신 결과 — 항목마다 가장 최근 실행  ▾ ]
   자동 실행 (suite_logs)   2026-09-29 16:48 · 5항목 · SM-S928N · 7.21.0-stag
   릴리스 (엑셀 기입값)      2026.09.23 · GME App 7.21.0 (NewApp)
```
**과거 실행·릴리스를 고르면 읽기 전용이다.** 굳은 기록을 고치면 기록인 의미가 없다.

⚠️ 지금 이 셀렉트는 **184건 중 28건만** 보게 된다(§1). 이력 위치를 먼저 정해야 반쪽이 아니게 된다.

### 목록
`ID · Pri · Depth · 확인 문구 · 매핑 · Android · iOS · Comment`

- **ID 가 맨 왼쪽 고정 키. 행 번호는 보여주지 않는다** — 보이면 사람이 그걸로 생각한다
- **매핑은 한 줄 텍스트** (`18_Telecom [01]` / `매핑 안 됨` / `자동화 불가 · 생체인증`)
  - 셀렉트를 안 쓰므로 **저장 시점에 `run_suite -DumpJson` 목록과 대조**해 없는 이름이면 빨갛게 표시한다.
    입력은 자유롭게 하되 틀린 건 저장 전에 드러난다
- **확인 문구는 인라인 편집**, 고친 행은 저장 전까지 표시가 남는다
- **미매핑은 배경색**으로 — 숫자가 아니라 눈으로 보인다
- 진척은 3분할: `자동 168 · 자동화 불가 37 · 미분류 208`
  (한 덩어리로 두면 "245행 더 자동화하면 되겠네"로 잘못 읽힌다)

### 실행 결과에서 보이는 모습
실행 이력의 항목을 펼치면 그 실행이 **무엇을 확인했고 무엇을 안 덮었는지** 나온다.
```
18_Telecom — PASS        확인함 1 / N-A 7 / 미커버 0
```
**"덮지 않음"을 같이 보여주는 것이 핵심**이다. 확인한 것만 보이면 41개 항목이
413행 중 무엇을 남기는지가 안 보인다.

## 8. 저장 — DB 는 아직 아니다

28건 898K 다. SQLite 가 의미 있어질 규모의 근처도 아니다.
문제는 크기가 아니라 **무엇을 어디에 두느냐**다.

### 데이터를 성격으로 가른다
| | 실행 산출물 | 판단 데이터 |
|---|---|---|
| 예 | 로그 · SUMMARY · 스크린샷 | **매핑 · 수동 결과 · 덮어쓴 사유** |
| 개인정보 | 있다 | 없다 |
| 누가 만드나 | 기계 (덧붙이기만) | 사람 (고치고 되돌린다) |
| 둘 곳 | 디스크, git 제외 | **git** |

⛔ 매핑·수동결과·사유를 로그 옆에 두면 **git 에 못 들어가고 백업도 이력도 없어진다.**
   하필 그것들이 되돌리기가 가장 중요한 데이터다.

### 지금 해야 할 세 가지 (DB 아님)
1. **기계가 읽을 산출물을 따로 만든다.** `runner.read_history` 는 지금 `SUMMARY.md` 를
   정규식으로 파싱한다 — 그건 **사람이 읽는 문서**다. 형식을 손보면 조용히 깨진다.
   → `suite_logs/<시각>/result.json` 을 같이 떨군다. 나중에 DB 로 갈 때도 그게 적재 소스다.
2. **실행 시점 스냅샷을 굳힌다.** `suite_logs/<시각>/checklist.json` 에
   그때의 ID·문구·결과를 박는다. 이게 없으면 **행 하나 지웠다고 지난달 결과가 달라진다.**
3. **실행 이력의 위치를 하나로 정한다.** 다른 PC 실행분 포함.

### DB 로 갈 신호
- **다른 PC 실행분까지 한 화면에서 봐야 한다** ← 이미 와 있다.
  다만 답이 DB 가 아니라 "결과 JSON 만 한 곳에 모으기"일 수 있다
- 실행이 수천 건이 되어 전체 스캔이 느려진다 (지금 28건, 체감 0)
- "체크리스트 ID 하나의 릴리스별 이력" 같은 교차 질의가 일상이 된다
- 여러 사람이 동시에 쓴다

그때도 첫 선택은 **SQLite**(파일 하나, 서버 불필요). 단 **판단 데이터까지 넣지 말 것** —
바이너리라 git diff 가 안 되고 사람이 손으로 못 고친다.

## 9. ⛔ 하지 말 것

**행 번호로 묶지 말 것.** 키는 `id` 다. §3.

**열 문자를 박지 말 것.** 릴리스가 추가될 때마다 결과 열이 밀린다.
현재 Android 가 `I` 인 것은 이번 릴리스 기준일 뿐이다 → **머리글 문구로 찾는다.**

**`write_result.py` 로 SharePoint 정본에 쓰려 하지 말 것.**
xlsx 를 zip 으로 열어 시트 XML 을 갈아끼우는 방식이라 **로컬 파일 전제**다.
OneDrive 동기화 업로드는 `UPLOAD FAILED` 기록이 있다.
→ 정본 쓰기는 `gme_excel.py`(Graph PATCH). 다만 그 파일의 **ID·머리글로 찾는 방식과
`--dry-run`** 은 그대로 가져올 값어치가 있다.

## 11. 위험 — 거짓 통과가 승격된다

체크리스트에 `Pass` 를 찍는 건 **"사람이 안 봐도 된다"**는 뜻이다.
그런데 이 저장소에는 거짓 통과 이력이 여럿이다.

- `21_Card [13]~[19]` — EXIT=0 인데 토글이 하나도 안 움직였다
- `21_Card [21]` — `tapOn "카드 취소"` 뒤 `assertVisible "카드 취소"` 라 행 라벨이 남아 항상 통과
- `04_Menu_History` 인바운드 구간 — 실검증 없이 통과하고 있었다

자동 기입은 이런 것을 **릴리스 판단 근거로 승격시킨다.** 대책:
- 출처와 실행 stamp 를 반드시 남긴다 (§5) → 로그로 되짚을 수 있게
- 자동 `Pass` 가 처음 붙는 영역은 **한 번은 사람이 표본 확인**하고 넘어간다

### 인증
토큰은 `~/.gme_excel_token.json`, **본인 권한**이다. refresh 가 만료되면 `login` 이
브라우저를 띄워야 하는데 **서버는 그걸 못 한다.**
- "SharePoint 연결됨/끊김" 상태와 재로그인 안내를 둔다
- 끊겨도 **읽기 화면은 캐시로 계속 동작해야 한다**
- 서버가 개인 토큰을 쥐므로 **`127.0.0.1` 바인딩을 절대 풀지 말 것** (`server.py` 현재 그렇다)
