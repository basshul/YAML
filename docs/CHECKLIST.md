**방향**: web-runner 에 체크리스트 화면을 새로 그리고 **매핑과 편집을 거기서 한다.**
엑셀은 당분간 정본으로 두되, 화면이 충분히 자라면 그때 정본 이동을 판단한다.
버릴지 말지는 지금 정하지 않는다 — 어느 쪽으로도 갈 수 있게 짓는 것이 이 문서의 목표다.

## 2. 방향 — web-runner 가 엑셀의 "프론트엔드"가 된다

정본을 옮기는 것과 **엑셀을 안 보게 되는 것**은 다른 일이다. 후자만 먼저 한다.

- 매핑·편집·결과 확인을 전부 web-runner 화면에서 한다
- 고친 값은 **그 셀만** 엑셀에 PATCH 한다 (동시편집·서식·댓글 안전)
- 매핑은 엑셀이 아니라 **저장소**에 둔다 → 엑셀을 나중에 놓아도 남는다

이러면 "엑셀을 안 본다"가 달성되면서, 정본 이동에 딸려오는 부채(백업·이력·동시편집·접근성)를
지금 지지 않는다. 6개월 뒤 아무도 엑셀을 안 열게 되면 **그때가 옮기기 가장 싼 순간**이다.

### 양쪽 문을 열어두는 원칙 셋
1. **저장 형식을 엑셀에 묶지 않는다.** 중립 JSON + 엑셀 어댑터 한 겹. 떼면 그만이다.
2. **엑셀 고유 기능에 의미를 싣지 않는다.** 조건부 서식 색이나 셀 댓글에 판단을 담으면
   나중에 **옮길 수 없는 정보**가 된다. 판단은 값으로, 전용 필드에.
3. **읽기는 캐시로.** 엑셀이 느리거나 인증이 끊겨도 화면이 돌아야,
   "없어도 되네"가 실제로 체감되고 그게 판단 근거가 된다.

### "엑셀이 필요 없는 상태"의 조건
- [ ] 413행을 web-runner 에서 읽고 고칠 수 있다
- [x] ~~릴리스가 여러 개 쌓인다~~ — **해당 없음.** 엑셀을 임시 작업 시트로 쓰기로 해
      릴리스 이력은 엑셀이 아니라 저장소(`result.json`)가 갖는다(2026-09-30)
- [ ] Priority · Depth · Comment 가 다 들어간다
- [ ] **iOS 결과를 기록할 자리가 있다** — iOS 도 추후 web-runner 로 실행한다
      (자동 기입은 **Android 안정화 후**, 2026-09-30 확정. 그때까지는 수동 입력 칸으로 둔다)
- [ ] 백업·되돌리기가 된다 (JSON 을 git 에 두면 대부분 공짜)
- [ ] 남에게 보여줄 방법이 있다 ← localhost 라서 이게 제일 오래 남는다

## 3. ID — 위치로 만들면 안 된다

`build_checklist_structure.py` 는 ID 를 위에서부터 센다.
```python
seq[code] += 1
d["id"] = "%s-%03d" % (code, seq[code])   # REG-001, REG-002 ...
```
**Registration 중간에 한 행이 삽입되면 그 아래 `REG-*` 가 전부 밀린다.**
`_bb_mapping.json` 의 "행 +1" 사고와 같은 문제가 옷만 갈아입은 것이다.

→ **ID 는 한 번 부여해 시트에 써 넣고 고정한다. 절대 재생성하지 않는다.**
   새 행은 그 영역 최대 번호 +1. 이게 안 되면 이 문서의 나머지가 전부 성립하지 않는다.

## 4. 결과 값 네 가지

정본에 실제로 쓰이는 값만 쓴다. 셀렉트로 고정해 자유 입력을 막는다.

| 값 | 뜻 | 누가 넣나 |
|---|---|---|
| `Pass` | 확인했고 정상 | 자동 / 수동 |
| `Fail` | 확인했고 결함 | 수동 (**자동 Fail 은 확인 대기로 둔다** — §5) |
| `Not Test` | 확인하지 못함 | 수동만. **자동으로는 넣지 않는다** |
| `NA` | **해당 없음** — 확인할 화면·기능이 없음 | 자동 (`run_suite` 의 `na`) / 수동 |

⚠️ **`Not Test` 와 `NA` 를 섞으면 "남은 일"을 셀 수 없게 된다.**
`Not Test` = 못 했다(언젠가 해야 함) / `NA` = 할 것이 없다(영영 없음).

실제 예:
- Telecom `[02]~[08]` = **`NA`** — 홈 그리드가 외부 웹으로 바뀌어 **확인할 화면이 없다**
- 생체인증 충전 = **빈칸** — 화면은 있는데 자동화가 못 닿아 **아직 아무도 확인하지 않았다**

### 자동화 불가 행 (2026-09-30 확정)

- **매핑 칸에 `매핑 안 됨 (자동화 불가)`** 로 적는다. 「매핑 안 됨」의 한 갈래로 보이게 둔다
- **결과는 비워 둔다**(`—`). `Not Test` 를 자동으로 넣지 않는다 —
  자동화가 못 하는 것과 아무도 확인하지 않은 것은 다르고, 사람이 손으로 확인하면 `Pass` 가 된다
- **왜 못 하는지는 Comment 에** 남긴다(예: `(aos) 자동화 불가 — 생체인증 필요`)

⚠️ 종전에 「자동화 불가는 `Not Test`」로 정했다가 **2026-09-30 에 비워 두는 것으로 바꿨다.**
`Not Test` 는 엑셀에 실제로 쓰이는 값이라(9건) **선택지에는 남기되 자동으로는 넣지 않는다.**

⚠️ 표기가 자유 텍스트라 오타(`자동화불가`, `자동화 불가능`)면 집계에서 빠진다.
→ **화면 표시는 이 문구로, 저장은 상태값으로** 두는 것이 안전하다.

**화면에 보이는 글자가 곧 기입될 값이어야 한다.** `N-A` 로 보여주고 `NA` 를 쓰면
정본의 `pass`(소문자) 오염과 같은 부류의 사고가 난다.

### 기입 대상 열 — 언제나 `I`

**릴리스 버전을 보지 않는다**(2026-09-30 확정).
자동화 결과는 항상 **`I11` 에서 시작해 `I423` 까지**(= 데이터 413행, §1) 들어간다.
`I10` 이하는 헤더(8~9행)와 여백이므로 건드리지 않는다.

릴리스마다 2열 묶음(iOS + Android)이 옆으로 늘어나는 구조지만,
`Checklist(Basshu)` 는 **임시 작업 시트**로 쓰므로 릴리스 이력을 엑셀에 쌓지 않는다.
→ 실행 이력의 정본은 **저장소**다(`result.json` + 수동 판단, §8).

⚠️ 열을 고정하는 대가: **앞쪽에 열이 삽입되면 `I` 가 다른 칸을 가리킨다.**
값은 그대로 채워져서 **틀려도 티가 안 난다.**
→ 저장 직전에 **`I9` 가 `Android Result` 인지** 한 칸만 읽어 확인하고 진행한다(호출 1회).
   이 가드가 §9 의 「열 문자를 박지 말 것」 을 대신한다.

## 5. 출처(provenance) — 값보다 중요하다

**모든 결과 칸은 셀렉트다. 자동으로 채워진 칸도 사람이 고칠 수 있다.**
외부 요인·셋팅 불량으로 Fail 이 났지만 사람이 보면 정상인 경우가 충분히 있다.

대신 **고치면 출처가 남는다.** 셀렉트만 두면 그 `Pass` 가 실행에서 나온 건지
사람이 고친 건지 나중에 알 수 없게 된다.

```
[ Pass  ▾ ]                    [ Pass  ▾ ]  ← 테두리 주황
자동 · 09-29 16:48              수동 덮음 · 자동은 Fail · 09-29 15:36
```

**자동 `Fail` 은 체크리스트에 바로 기입하지 않고 「확인 대기」로 둔다.**
외부 요인으로 난 Fail 이 릴리스 판단에 그대로 실려서도 안 되고,
조용히 묻혀서도 안 된다 → 사람이 최종값을 고르되 그 판단이 기록에 남는다.

**덮어쓸 때는 Comment 에 사유가 있어야 저장된다.**
3개월 뒤 같은 케이스가 또 Fail 날 때 "그때 왜 덮었더라"를 답할 수 있는 건 그 한 줄뿐이다.

Comment 규칙 (2026-09-30 확정):
- ★ **사유의 정본은 저장소**다(§2 ② 의 `reason`). 엑셀 `J` 열에는 **사람이 읽을 한 줄만 덧붙인다**(사본).
  한 칸에 플랫폼·실행이 섞여 쌓이는 구조라, 「이 사유가 어느 실행 건인지」를 기계가 읽어낼 수 없다.
  엑셀을 정본으로 두면 **그것 하나 때문에 엑셀을 못 놓게 된다**(§2 의 방향과 어긋난다)
- **엑셀 J열에 원래 있던 메모는 읽어서 같이 보여주되 고치지 않는다.** 그건 엑셀 소유다
  → 화면은 둘을 구분해 보여준다(원래 메모는 읽기 전용, 새 사유는 편집 가능)
- **릴리스마다 열이 따로 없고 한 칸을 계속 쓴다** → 덮어쓰지 말고 **줄을 덧붙인다**
- 접두사는 기존 관례대로: `(aos)` / `- ios :` / `- aos/ios :`

## 6. 단위 불일치 — 41 vs 413

```
run_suite   41 항목(플로우)  →  PASS / FAIL / SKIP
체크리스트  413 행(확인 항목) →  Pass / Fail / Not Test / NA
```

### 매핑 단위 (2026-09-30 확정)

```
체크리스트 1행  =  1 케이스
yaml 1개       =  1 시나리오  (그 안에 케이스가 여럿)
```
→ 매핑은 **`시나리오 [케이스]`** 다. 예: `TEL-001 ↔ 18_Telecom [01]`.
   Telecom 은 yaml 1개에 케이스 8개이고 체크리스트도 8행이라 1:1 로 맞는다.

### 그래서 케이스 단위 결과가 **필요**하다

문제는 매핑이 아니라 **결과가 플로우 단위로 온다**는 것이다.

- 플로우 FAIL ≠ 그 안 케이스 전부 Fail (앞부분은 통과했을 수 있다)
- 플로우 PASS ≠ 그 안 케이스 전부 Pass (`NA` 가 섞인다)

실패 지점 **이후** 케이스는 "확인함"이 아니라 **미확인**이다. Fail 로 싸잡으면
하지 않은 확인을 했다고 적는 셈이 된다.

★ 1행 = 1케이스로 정한 이상, **행 하나를 채우려면 그 케이스의 결과를 알아야 한다.**
그래서 §10 의 케이스 단위 마커(4단계)는 **선택이 아니라 필요한 경로**다.
그때까지는 **플로우가 PASS 일 때만** 그 안 케이스들을 채우고, FAIL 이면 사람이 판단한다.

※ 케이스 단위 정보가 **부분적으로는 이미 있다** — `run_suite.ps1` 의 `$Suite` 가
`blocked=@("06","07")` / `na=@("02",...)` 처럼 **케이스 번호**를 들고 있다.
`NA`·BLOCKED 는 여기서 오고, 없는 건 케이스별 **PASS/FAIL** 뿐이다.

### 결과 기준 (상단 셀렉트)

**과거 실행·릴리스를 고르면 읽기 전용이다.** 굳은 기록을 고치면 기록인 의미가 없다.

과거 184건은 대상이 아니므로 **2026-09-30 이후 실행부터** 쌓인다.

### 목록
`ID · Pri · Depth · 확인 문구 · 매핑 · Android · iOS · Comment`

- **ID 가 맨 왼쪽 고정 키. 행 번호는 보여주지 않는다** — 보이면 사람이 그걸로 생각한다
- **매핑은 한 줄 텍스트** (`18_Telecom [01]` / `매핑 안 됨` / `자동화 불가 · 생체인증`)
  - 셀렉트를 안 쓰므로 **저장 시점에 `run_suite -DumpJson` 목록과 대조**해 없는 이름이면 빨갛게 표시한다.
    입력은 자유롭게 하되 틀린 건 저장 전에 드러난다
- **확인 문구는 인라인 편집**, 고친 행은 저장 전까지 표시가 남는다
- **미매핑은 배경색**으로 — 숫자가 아니라 눈으로 보인다
- 진척은 3분할: `자동 168 · 자동화 불가 37 · 미분류 208`
  (한 덩어리로 두면 "245행 더 자동화하면 되겠네"로 잘못 읽힌다)

### ★ 목록은 언제나 전체다 (2026-09-30 확정)

**실행한 항목에 따라 목록이 줄어들지 않는다.** 기본은 **전체 413행**이고,
영역별로 이어서 보여준다. 좁히는 것은 **필터로만** 한다.

→ 「이번에 테스트한 것만」 은 필터 축 하나로 제공한다:
```
이번 실행 — 전체 (413행)        ← 기본
이번 실행에서 테스트한 것만
이번 실행에서 빠진 것만          ← 이 실행이 무엇을 안 덮었는지
```
기준은 상단 「결과 보기」 에서 고른 실행이다.
`최신 결과` 를 고른 상태에서는 기준이 정해지지 않으므로 전체만 보인다.

⚠️ **실행 결과가 목록을 좌우하게 만들지 말 것.** 체크리스트는 「해야 할 일 전부」의
목록이지 「이번에 한 일」의 목록이 아니다. 실행에 따라 줄어들면
**안 덮은 행이 화면에서 사라져** 커버리지가 실제보다 좋아 보인다.

목업의 Telecom·HOME·Card 는 서로 다른 상태를 보이려고 **발췌한 14행**이다
(실제로는 413행이 이어진다).

⚠️ **413행을 한 번에 그리는 비용은 아직 안 따져봤다.** 행마다 셀렉트가 2개,
편집 가능한 칸이 3개라 DOM 이 2,000 노드를 넘는다.
느리면 영역 단위 접기나 가상 스크롤이 필요한데, **그건 만들어 보고 정한다** —
미리 최적화하면 쓰지도 않을 복잡도를 먼저 진다.

### 화면 구성 (2026-09-30 확정)

**실행 화면과 체크리스트를 합친다.** 체크리스트가 메인 화면이고,
종전 실행 화면의 「테스트 선택」 패널은 없앤다 — **체크리스트 자체가 선택 화면**이 된다.

```
[머리] 체크리스트 413행 · 결과 기입 I11:I423     [다시 읽기][저장] | [실행][전체 실행][중단]
[환경] 서버 · 기기 · 플랫폼
[결과 보기] / [진척] / [필터]
[표]  ☐ ID · 중요도 · 분류 · 확인 항목 · 매핑 · Android · iOS · Comment
[선택] 선택 9행 → 시나리오 2개 · 예상 5분
[하단] 기입 대기 / 사람 수정 · 되돌리기 · 저장
```

★ **행은 케이스 단위지만 실행은 시나리오 단위다.** 케이스 하나만 돌릴 수 없다
(§6) → 행을 고르면 **그 행이 속한 시나리오가 통째로** 돈다.
`21_Card` 는 1행만 골라도 22개 케이스가 전부 돈다 → **선택 요약에 이를 드러낸다**:
`선택 9행 → 시나리오 2개 · 예상 5분`. 안 그러면 "1행 골랐는데 왜 5분이나 걸리지"가 된다.

### 실행 상세 — 별도 페이지

**진행 상황과 로그는 체크리스트 화면에 두지 않는다.** 413행이 본문인 화면에 로그까지
얹으면 둘 다 안 보인다. 실행을 누르면 상세 페이지가 열려 진행이 보이고,
끝나면 그대로 결과 페이지가 된다.

여기에 종전 「실행 결과에서 보이는 모습」 이 들어간다:
실행 이력의 항목을 펼치면 그 실행이 **무엇을 확인했고 무엇을 안 덮었는지** 나온다.
```
18_Telecom — PASS        확인함 1 / N-A 7 / 미커버 0
```
**"덮지 않음"을 같이 보여주는 것이 핵심**이다. 확인한 것만 보이면 41개 항목이
413행 중 무엇을 남기는지가 안 보인다.

## 8. 저장 — DB 는 아직 아니다

28건 898K 다. SQLite 가 의미 있어질 규모의 근처도 아니다.
문제는 크기가 아니라 **무엇을 어디에 두느냐**다.

### 층이 넷이다 — 무엇이 무엇을 덮어쓰지 않는가

```
① result.json       기계가 쓴다 · **불변** · git        실행 하나당 한 개
② 수동 판단          사람이 쓴다 · **덧붙이기** · git    판단 하나당 한 줄
③ 화면에 보이는 값   ①+② 를 겹쳐 **계산** · 저장하지 않는다
④ 엑셀               〈저장〉을 누를 때 해당 셀만 PATCH — ① 과 ② **둘 다** 대상
                    Comment 는 ② 이 정본이고 여기엔 **사람이 읽을 한 줄만** 간다(§5)
```

**① 을 사람이 고치면 안 된다.** 고치는 순간 "자동은 Fail 이었다"가 사라지고,
그러면 §5 의 출처 표시(`수동 덮음 · 자동은 Fail`)를 만들 수가 없다.
실행 기록은 **그 실행에서 무슨 일이 있었는지**를 말하는 것이지
**우리가 어떻게 판단했는지**를 말하는 것이 아니다. 둘을 같은 파일에 담으면 되돌릴 수 없다.

수동 수정은 ② 에 한 줄씩 쌓는다:
```json
{ "id": "CRD-002", "platform": "android", "release": "2026.09.23",
  "value": "Pass", "source": "manual",
  "overrides": { "stamp": "2026-09-29_153634", "autoValue": "Fail" },
  "reason": "(aos) 자동 Fail — 기기 세션 만료로 진입 실패. 수동 재확인 결과 정상",
  "at": "2026-09-30T14:02:11" }
```
같은 항목을 또 고치면 **덮어쓰지 않고 한 줄 더 쌓는다.** 화면은 마지막 줄을 보여준다.
그래야 "언제 뭘 어떻게 바꿨나"가 남는다.

### 저장 대상은 둘이다 — 「기입 대기」 와 「사람 수정」

```
기입 대기 12건(자동)  ← 실행이 채웠지만 **아직 엑셀에 없는 값**
사람 수정  4건        ← 문구 · 매핑 · 수동 결과
```

**실행만으로는 엑셀이 채워지지 않는다.** 저장을 눌러야 나간다.
→ 화면에 기입 대기 건수를 드러내고, 각 행의 출처 줄에도 `미기입` 을 표시한다.
   안 그러면 자동 결과가 화면에만 있고 엑셀은 조용히 낡는다.

⛔ **자동 `Fail` 은 기입 대기에 들어가지 않는다.** 「확인 대기」라서(§5),
사람이 최종값을 고른 뒤에야 「사람 수정」 쪽으로 넘어간다.

엑셀에 이미 같은 값이 있으면 건너뛴다 — 안 그러면 실행마다 413칸을 전부 PATCH 하게 된다.

### ✓ 검토했으나 채택하지 않은 것: 내보내기 방식

「정본에 자동 기입하지 말고 **같은 형태로 내보내 사람이 붙여넣자**」를 검토했다(2026-09-30).
충돌·부분실패·릴리스 열 선택이 한꺼번에 사라지는 장점이 있었지만, **채택하지 않았다.**

이유: `Checklist(Basshu)` 는 **개인 작업 시트**라 동시편집 충돌이 애초에 거의 없다.
그리고 붙여넣기에는 PATCH 에 없는 위험이 둘 있다.
- **행 정렬에 전적으로 의존한다.** 내보낸 뒤 정본에 행 하나가 들어가면 그 아래가 통째로 어긋나고,
  **값은 다 채워져 있어서 티가 안 난다** (`_bb_mapping` "행 +1" 사고와 같은 부류)
- **Comment 를 덮어쓴다.** §5 의 「덮어쓰지 않고 줄을 덧붙인다」 규칙이 깨진다.
  PATCH 는 「기존 내용 + 새 줄」 로 정확히 쓸 수 있다

→ 같은 논의를 다시 하지 않도록 남겨 둔다. **시트가 공유로 바뀌면 재검토 대상**이다.

### 저장은 버튼을 눌러야 한다 (자동 저장 아님)

- 저장이 **SharePoint 셀 PATCH** 라 네트워크를 탄다. 셀렉트 하나 건드릴 때마다 왕복하면
  느리고, 실패했을 때 **화면과 엑셀이 어긋난다**
- 덮어쓸 때는 **Comment 사유가 필수**(§5)인데, 자동 저장이면 사유를 쓰기도 전에 값이 나간다

단 **입력 중인 초안은 자동으로 로컬에 남긴다.** 셀렉트 몇 개 바꾸고 브라우저를 닫았는데
날아가면 안 된다. 화면의 "저장 안 된 변경 N건" 표시가 그 상태다.

**개인 시트여도 남는 문제 셋** (§12 에 올려 뒀다)
1. **부분 실패** — 셀 30개 중 12번째에서 끊기면 앞 11개는 이미 나갔고 롤백이 안 된다
   → **실패한 셀만 최대 3회 재시도**한다(2026-09-30 확정). 3회 뒤에도 실패하면 멈추고
     **어느 셀이 남았는지 보여준다** — 조용히 넘어가면 그 행만 엑셀이 낡는다.
     성공한 셀은 다시 보내지 않는다(「이미 같은 값이면 건너뛴다」 규칙과 같은 이유)
2. **어느 릴리스 열에 쓸 것인가** — 실행 빌드 `7.21.0-stag` ↔ 엑셀 열 `2026.09.23 GME App 7.21.0 (NewApp)`
3. ~~같은 항목을 하루에 여러 번 돌렸을 때~~ — **규칙을 두지 않는다**(2026-09-30 확정).
   시트는 임시 작업 공간이고 기입값은 사람이 통제한다. 화면은 실행별 결과를 그대로 보여주고,
   무엇을 엑셀에 넣을지는 사람이 고른다

⚠️ 충돌은 개인 시트라 거의 없지만 **본인이 엑셀과 화면을 동시에 열어두는 경우**는 실재한다
→ 저장 직전에 대상 셀만 다시 읽어 값이 달라졌으면 멈춘다.

### ⚠️ 강제종료된 실행은 기록이 없다

`result.json` 은 `SUMMARY.md` 와 마찬가지로 **실행이 끝날 때 한 번** 쓰인다.
`-StopOnFail` 이나 복구 실패로 인한 `aborted` 는 스크립트가 정상 종료하므로 기록이 남지만,
**프로세스가 죽으면 둘 다 안 남는다**(백그라운드 실행이 PC 메모리 부족으로 강제종료된 이력이 있다).
→ 이력이 비어 보일 때 "안 돌았나?"로 오해하지 말 것. 지금 고칠 일은 아니고, 아는 것으로 족하다.

### 데이터를 성격으로 가른다
| | 실행 산출물 | 판단 데이터 |
|---|---|---|
| 예 | 로그 · SUMMARY · 스크린샷 | **매핑 · 수동 결과 · 덮어쓴 사유** |
| 개인정보 | 있다 | 없다 |
| 누가 만드나 | 기계 (덧붙이기만) | 사람 (고치고 되돌린다) |
| 둘 곳 | 디스크, git 제외 | **git** |

⛔ 매핑·수동결과·사유를 로그 옆에 두면 **git 에 못 들어가고 백업도 이력도 없어진다.**
   하필 그것들이 되돌리기가 가장 중요한 데이터다.

  다만 답이 DB 가 아니라 "결과 JSON 만 한 곳에 모으기"일 수 있다

- "체크리스트 ID 하나의 릴리스별 이력" 같은 교차 질의가 일상이 된다
- 여러 사람이 동시에 쓴다

그때도 첫 선택은 **SQLite**(파일 하나, 서버 불필요). 단 **판단 데이터까지 넣지 말 것** —
바이너리라 git diff 가 안 되고 사람이 손으로 못 고친다.

## 10. 단계

**0. ID 를 시트에 고정으로 박는다** ← 선결. §3

**1. 읽기 캐시 + 체크리스트 화면**
`gme_excel.py get(--json)` → `checklist_cache.json` → `/api/checklist`.
매핑은 `checklist_map.json`(git). 진행 중인 엑셀 매핑 작업을 **초기 데이터로 임포트**한다
— 형식 그대로 주면 임포터가 흡수한다. 정리하지 않아도 된다.

**2. 실행 결과에 커버리지 표시** ← 원래 목적이 여기서 나온다. §7

**3. 편집 → 셀 PATCH 되돌려쓰기** (문구·결과·Comment)

**4. 케이스 단위** — Maestro `label:` 로 케이스 경계를 로그에 찍는다
(1행 = 1케이스로 정해져 **필요한 경로**가 됐다, §6)
```yaml
- evalScript:
    script: ${true}
    label: "COVERS TEL-001"
```
✅ 문법 확인됨(2026-09-30, maestro 2.10.0 jar): `YamlEvalScript` 필드 = `script`/`label`/`optional`,
`EvalScriptCommand` 에 `label`·`getLabel` 존재. 추측이 아니다.
저장소에 `label:` 사용이 **0건**이라 새 규약이고, 41개 파일을 손대므로 **순서상 뒤**에 둔다.
파일 단위 점진 도입이 되며, 마커 없는 플로우는 플로우 단위로 남는다
→ 커버리지가 높은 시나리오부터 넣으면 이른 시점부터 효과가 난다.

**5. (한참 뒤) 정본 이동 논의** — §2 의 조건이 다 채워졌을 때

## 11. 위험 — 거짓 통과가 승격된다

체크리스트에 `Pass` 를 찍는 건 **"사람이 안 봐도 된다"**는 뜻이다.
그런데 이 저장소에는 거짓 통과 이력이 여럿이다.

- `21_Card [13]~[19]` — EXIT=0 인데 토글이 하나도 안 움직였다
- `21_Card [21]` — `tapOn "카드 취소"` 뒤 `assertVisible "카드 취소"` 라 행 라벨이 남아 항상 통과
- `04_Menu_History` 인바운드 구간 — 실검증 없이 통과하고 있었다

자동 기입은 이런 것을 **릴리스 판단 근거로 승격시킨다.** 대책:
- 출처와 실행 stamp 를 반드시 남긴다 (§5) → 로그로 되짚을 수 있게
- 자동 `Pass` 가 처음 붙는 영역은 **한 번은 사람이 표본 확인**하고 넘어간다

### 인증
토큰은 `~/.gme_excel_token.json`, **본인 권한**이다. refresh 가 만료되면 `login` 이
브라우저를 띄워야 하는데 **서버는 그걸 못 한다.**
- "SharePoint 연결됨/끊김" 상태와 재로그인 안내를 둔다
- 끊겨도 **읽기 화면은 캐시로 계속 동작해야 한다**
- 서버가 개인 토큰을 쥐므로 **`127.0.0.1` 바인딩을 절대 풀지 말 것** (`server.py` 현재 그렇다)
